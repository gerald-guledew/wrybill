# M0: Foundations

**Goal:** one commit produces working `wrybill` binaries for macOS (Intel and Apple Silicon), Windows and Linux, and `wrybill doctor` runs on each, including one real old laptop.

Read first: [AGENTS.md](../../AGENTS.md), then sections 7.5, 10.3, 11.6, 13, 14, 14.1 and 15 of [the spec](../SPEC.md).

## What to build

1. **Workspace.** A Cargo workspace on stable Rust (2024 edition), with the toolchain pinned in `rust-toolchain.toml`. Create the seven crates in SPEC 15.1 and `apps/wrybill-cli`. M0 writes code in three places: `wrybill-config` (config, paths and keychain), the system-profile module of `wrybill-tools`, and `wrybill-cli` (the `doctor` and `keys set` commands, and logging). The other crates stay as empty shells. `apps/wrybill-desktop`, `prompts/` and `evals/` arrive with their own milestones.
2. **Config.** Load `config.toml` from `~/.wrybill` (or wherever `WRYBILL_HOME` points) and validate it against SPEC 13.3: types, allowed values, defaults and the listed checks, with clear, specific error messages. A missing file isn't an error.
3. **Keychain.** `wrybill keys set <provider>` stores an API key in the OS keychain through the `keyring` crate. The key is typed at a hidden prompt or piped in, never passed as an argument. The config holds references such as `keychain:wrybill/anthropic`. On headless Linux with no secret service, an `env:VARIABLE_NAME` reference works too, with a warning (SPEC 11.6).
4. **Logging.** `tracing` with JSON output, kept under `~/.wrybill/logs/`. No telemetry.
5. **`wrybill doctor`.** Prints the system profile and checks the setup.
   - **Profile (SPEC 10.3):** OS and version; chip and CPU features, including AVX and AVX2; RAM, total and free; disk; graphics; shells; package managers (Homebrew, winget, Scoop, apt, dnf, pacman); runtimes (git, Python, Node.js, Java, Docker); browsers (Chrome, Edge, Brave, Chromium, Firefox); whether the network is up; and whether the OS still gets security updates.
   - **Setup:** where the config file is and whether it's valid, or that defaults are in use; whether the OS keychain can be reached; and which key references in the config resolve. It never prints a key.
   - It still runs when the config is invalid: it reports the errors, then prints the profile.
   - The security-updates check uses a small built-in table of macOS and Windows versions, filled in from the vendors' support pages when it's written (record the date checked). It says "unknown" for anything else.
   - The network check uses what the OS reports and sends no requests to third-party sites.
   - The profile is worked out fresh on every run. Caching, sandbox status and the disk used by checkpoints come with later milestones.
6. **Supply chain.** A `deny.toml` that allows the permissive licences Rust dependencies usually carry (MIT, Apache-2.0, BSD, ISC, Zlib, Unicode-3.0 and the like) and flags anything else for a recorded decision. `cargo audit` and `cargo deny` run in CI.
7. **CI.** GitHub Actions runs formatting, linting, tests and the supply-chain checks on every push and pull request, and builds release binaries for every target below.

## Build targets

| Target | Suggested GitHub runner |
|---|---|
| `x86_64-apple-darwin` | `macos-15-intel` |
| `aarch64-apple-darwin` | `macos-latest` |
| `x86_64-pc-windows-msvc` | `windows-latest` |
| `aarch64-pc-windows-msvc` | `windows-11-arm` |
| `x86_64-unknown-linux-gnu` and `x86_64-unknown-linux-musl` | `ubuntu-22.04` |
| `aarch64-unknown-linux-gnu` and `aarch64-unknown-linux-musl` | `ubuntu-22.04-arm` |

These runner names were current on 3 October 2026. Check GitHub's list before relying on them.

- One CLI binary per target. The universal macOS build belongs to the desktop app (M7).
- Release builds use the default x86-64 target. Never build with `target-cpu=native`.
- Intel Mac builds set `MACOSX_DEPLOYMENT_TARGET=10.15`.
- Windows builds link the C runtime statically, so nothing else needs installing.
- The `musl` builds are fully static.

## Not in M0

The agent loop, brains, the agent's tools, the Guardian, memory, the task store and the desktop app. The `system.profile` tool arrives in M1 and reuses the profile module written here.

## Done when

- [ ] One commit produces release binaries for every target above, and CI is green.
- [ ] `wrybill doctor` runs and reports correctly on macOS, Windows and Linux, including one real 2015-era laptop. Each tested machine is recorded in `docs/compatibility.md`.
- [ ] `wrybill keys set` stores a key in the OS keychain on each OS, and the config can reference it.
- [ ] Every check in SPEC 13.3 has a test, an invalid config produces a clear, specific error, and `wrybill doctor` runs on built-in defaults when there's no config file.
- [ ] No secrets in the repo, the logs or the tests, and no live API calls in tests.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` and `cargo deny check` all pass.
